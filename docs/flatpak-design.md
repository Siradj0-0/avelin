# Flatpak feasibility: design and test plan

**Status: design only; no Flatpak manifest or working package is provided.** This review covers the source at `030f6fb24a44520a9e6e74d1523404315764bc10`. A manifest that launches the current UI would be misleading: several labels and success messages describe the host, but its data and operations may be sandbox-scoped. Fixing that requires application changes outside the scope of this prototype. Do not build or distribute an unmodified app as a working system utility.

## Decision and constraints

The smallest viable future experiment is a **degraded, explicitly sandbox-aware build**: show only data whose origin is known, mark other host information unavailable, and disable host-changing actions unless a separately reviewed integration establishes their scope and result. This is a proposal, not implemented behavior. No helper, host shell, sandbox escape, blanket home/host mount, full session/system bus, or unrestricted device access is justified merely to make current labels appear to work. Even read-only host filesystem grants expose sensitive information and must have a specific, reviewed use. Flatpak normally isolates processes and files, filters D-Bus, and reserves paths including `/proc`; selected `/sys` subtrees are read-only by default, not a guarantee of complete host visibility. [Flatpak sandbox permissions](https://docs.flatpak.org/en/latest/sandbox-permissions.html)

| Feature in current code | Risk in a sandbox | Safe future behavior |
| --- | --- | --- |
| `system.os_name()`, `disk('/')`, `/proc/stat`, `/proc/meminfo`, CPU details and `/proc/swaps`; dashboard and System page | `/etc/os-release` can identify the runtime, `/` is the sandbox root, and proc readings or visible devices can differ by runtime/kernel/container. Numerical results are not proof of host provenance. `lspci` may be absent or incomplete. | Detect Flatpak (e.g. `/.flatpak-info`), default host-specific metrics, distribution, root storage, GPU and zram to unavailable. Only enable an individual reading after establishing and testing its origin; label sandbox readings as sandbox readings. Never replace unavailable with zero or infer host completeness from a successful read. |
| `storage.locations()` and `scan()` | XDG cache/data and `/var` are sandboxed or unavailable; the current labels imply host caches, trash, package archives, journals and Flatpak data. | Disable host-wide scan by default or expose only explicitly labeled app-private data. Never present an absent or inaccessible host directory as a complete, zero-sized host scan. Preserve existing scan bounds and partial-status semantics. |
| `actions.setting_state()` / `set_setting()` | A sandboxed `gsettings` schema/backend can be missing or app-scoped; a successful write and readback need not change the host GNOME session, despite the UI's claim. | Disable GNOME host preferences in the experiment. Portal Settings is read-only, limited to standardized toolkit settings and is not a general GSettings write API. Direct dconf permissions are broader than a per-key capability and require separate security review; do not use them as a shortcut. [Settings portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.Settings.html), [dconf access](https://docs.flatpak.org/en/latest/sandbox-permissions.html#dconf-access). |
| `powerprofilesctl` discovery and apply | Host executables are not automatically available inside the runtime; bundling a CLI alone does not grant access to the host daemon. System D-Bus is unavailable by default. | Initially disable the control and say unavailable in Flatpak. A later design could use a narrowly allowed system bus name for the daemon, not the entire bus, after verifying supported daemon names/versions, policy and authorization, and the privacy/security impact. Discover `Profiles`, read `ActiveProfile`, offer only advertised values, confirm explicitly, handle errors/authorization and read back the actual host state; absence or denial is unavailable, never success. The [daemon API](https://freedesktop-team.pages.debian.net/power-profiles-daemon/gdbus-org.freedesktop.UPower.PowerProfiles.html) documents the current object and properties. This is an investigation, not a promise of compatibility. |
| `gio trash --empty` and success message | `gio` being present does not establish access to or successful emptying of every host trash location. Current UI says trash was emptied after a zero exit status. | Disable empty-trash in Flatpak. The [Trash portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.Trash.html) sends an individually accessible file to trash via a read/write file descriptor; it is **not** a host-wide empty-trash API. Do not present it as one. If an alternative is ever proposed, separately review irreversible deletion, user confirmation, scope, partial failures and mounted volumes. |
| Release check in `updates` | The app automatically checks GitHub on startup; networking is disabled by default, and granting it changes privacy and permissions. | Disable the automatic check or explain and explicitly design network use before granting `--share=network`. Failure/offline must be honest. Prefer distribution-managed updates; an Open URI portal is not network permission for the app. |

## Future packaging implementation (not a manifest)

1. First implement and review explicit sandbox-aware capabilities and UI labels in the application, with unit tests. A wrapper that merely hides commands is insufficient: the current UI still scans, displays sandbox metrics as host metrics and enables `gio`-based trash. Changes to existing application files are deliberately not part of this design-only branch.
2. Choose a supported GNOME runtime/SDK version after verifying its Python 3, GTK 4, PyGObject, PyGObject Cairo bridge and pycairo availability; pin and build any missing dependencies from verified sources. Run `python3 -m avelin` with the installed module on the Python path. No particular runtime or dependency version has been validated here.
3. Use the existing application ID `io.github.siradj00.avelin` consistently for the future manifest, `Gtk.Application`, exported desktop file and icon; install the Python package, a launcher, desktop file and SVG icon into `/app` with ID-prefixed export names. Verify the desktop `Exec` invokes the installed launcher, not a source-tree path. Pin application sources to a commit or release checksum and pin third-party sources. A manifest declares `id`, runtime, runtime version, SDK, command, modules and sources. [Flatpak manifests](https://docs.flatpak.org/en/latest/manifests.html)
4. Start with only the display permissions needed by the tested toolkit/backend: Wayland and, if actually needed, fallback X11; assess X11's weaker isolation. Add IPC or rendering access only if a demonstrated need exists. No host/home filesystem, device-all, direct dconf, full bus, network, host-spawn or power-daemon permission by default. If a capability later needs an exception, document the exact grant, threat, alternative, tested behavior and user-visible consequence. Static permissions should remain minimal. [Permissions guidance](https://docs.flatpak.org/en/latest/sandbox-permissions.html)
5. Build locally, install to a disposable user installation and inspect exported metadata and effective permissions. This is not an instruction to publish to a remote or Flathub. The manifest should only be introduced once capability gating is present and the checks below pass.

## Acceptance and test plan

Use disposable VMs or test accounts with backups, a desktop session, Flatpak, `flatpak-builder`, the chosen matching SDK/runtime and portal backend. Record distro, desktop/session type, Flatpak, runtime/SDK and portal versions. Test GNOME on Wayland and, where supported, X11; test at least one non-GNOME desktop and missing portal/daemon cases. Do not run destructive tests against valuable personal data.

- **Build and launch:** run the existing unit suite and Python compilation, then `flatpak-builder --force-clean build-dir <manifest>` and a local user install from a local repo once a manifest exists. Confirm a clean rebuild, imports including the Cairo bridge, desktop/icon export, launch, and no traceback. Capture the runtime/SDK refs and versions. Check effective `flatpak info --show-permissions <app-id>` for the reviewed allowlist, and audit bus denials using Flatpak's debugging facilities. Fail if unreviewed broad permissions appear.
- **Truthful metrics:** compare UI to outside-sandbox `cat /etc/os-release`, `df -h /`, `cat /proc/meminfo`, `/proc/stat` and `/proc/swaps` as diagnostics, not as an assumption that they must agree. Exercise deliberately missing/restricted sources and different container conditions. Every unknown host value must be unavailable; sandbox-specific data must be labeled, and no runtime distribution or sandbox root presented as the host. Verify scan labels and partial/error status with controlled fixtures and no unintended host traversal.
- **Settings:** on a disposable GNOME session, record host `gsettings get` values before and after attempted Flatpak actions. Disabled controls must not change host state or report success. If a future supported host integration is proposed, test every allowlisted key, unsupported schemas, non-GNOME sessions, denied writes and host-side readback; restore each original value.
- **Power:** with and without the daemon, verify disabled/unavailable behavior. For any later integration, test advertised profile discovery, missing/denied bus access, denied authorization, timeout, daemon disappearance and host-side readback after confirmation; restore the original profile. No success message without verified host state.
- **Trash:** use only a disposable account/VM with dummy files in home trash and, if available, a disposable mounted volume. Confirm no sandbox action deletes them and no success message is displayed while the feature is disabled. Independently test any future proposal for cancellation, partial failure, each supported location and irreversible effects. The Trash portal's per-file move-to-trash is a different operation.
- **Network and failure paths:** verify the baseline makes no release request, behaves offline and doesn't claim a check succeeded. Exercise unavailable runtime services and inaccessible paths without crashes or fabricated success. Record logs, screenshots and exact versions/results.

**Go/no-go:** do not add or distribute a manifest until sandbox-aware UI and capability gates exist, permissions have been reviewed, a clean build/launch works, and the negative and host-readback tests above pass. Unvalidated integrations remain unavailable.
